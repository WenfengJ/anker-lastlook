- TODO：尚未开始

- DONE：已完成
- BLOCKED：缺少信息或条件，暂时无法推进

## 当前总目标

围绕 Anker eufy 智能安防赛题，完成一套能交差、能演示、能验证的 LastLook 参赛方案，并沉淀一套可指导前端和后台开发的工程规格。

当前产品收窄方向：

LastLook 是一个由 eufy 摄像头驱动的出门安全确认清单。首版只聚焦“用户出门后确认灶台是否关闭”，用 eufy 云台摄像头的预设位、拍照、补光/夜视、隐私区和设备状态，生成一张带证据的确认卡片。

### 4. 原型图需求说明

状态：DONE

目标：明确需要画哪些关键画面，后续可以交给设计工具或直接生成低保真原型。

最少需要 4 张关键状态：

- 出门后自动检查中
- 灶台已确认关闭
- 无法确认，锅挡住旋钮
- 异常，疑似未关闭

完成标准：

- 每张图都能对应 Demo 脚本中的一个关键时刻。
- 每张图都展示当前照片或证据入口。
- 状态文案清楚，不夸大系统能力。

建议文件：

- `docs/lastlook-prototype-spec.md`

### 5. 技术架构说明

状态：DONE

目标：说明 LastLook 如何使用 eufy 摄像头能力形成闭环。

需要包含：

- eufy 摄像头能力映射
- PTZ 预设位
- 拍照 / 视频帧采集
- 补光 / 夜视
- 隐私区
- 门锁或离家事件触发
- 图像比对逻辑
- 结果卡片生成
- App 通知
- 本地优先和隐私策略

完成标准：

- 评委能看出摄像头能力不是摆设。
- 技术路径足够克制，不依赖泛化物体识别。
- 能解释“已确认 / 无法确认 / 异常”三种结果。

建议文件：

- `docs/lastlook-technical-architecture.md`

### 6. 可验证指标与测试方案

状态：DONE

目标：把“可验证”落成测试方式。

建议指标：

- 确认耗时：从离家触发到结果卡片生成，目标 30 秒内。
- 无法确认率：测试不同光线、遮挡和角度下的无法确认比例。
- 用户信任：用户是否点开证据照片，是否减少折返检查。
- 异常识别准确性：旋钮明显偏离基准时能否标记异常。

完成标准：

- 每个指标都有测量方式。
- 每个指标都能用 Demo 或小样本测试解释。
- 不承诺无法验证的大规模效果。

建议文件：

- `docs/lastlook-validation-plan.md`

### E2. 前端功能规格

### E3. 后台接口规格

状态：DONE

目标：定义前端、检查引擎、设备模拟器之间的接口。

建议接口：

- `POST /checks/start`：开始一次检查
- `GET /checks/:id`：获取检查状态和结果
- `POST /baseline`：保存灶台基准照片
- `GET /baseline`：读取当前基准照片
- `GET /devices`：获取摄像头、门锁、插座等设备状态
- `POST /demo/scenario`：切换演示场景

完成标准：

- 每个接口都有请求参数、响应字段、错误码。
- 支持前端完成完整 Demo。
- 可以先用模拟数据实现。

建议文件：

- `docs/lastlook-api-spec.md`
